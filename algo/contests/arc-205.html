Solutions

A

Let's solve the problem for a single query spanning the entire grid. What if the grid consists of just white cells? Well, then the answer would just be 𝑛 ⋅𝑚 −2n⋅m−2 because we can iterate over the 2 ∗22∗2 subgrids in increasing order of (𝑥,𝑦)(x,y) (their top-left cell) and always just color (𝑥,𝑦)(x,y) black. This is optimal because (𝑥,𝑦)(x,y) won't affect any subgrids we consider in the future.

Ok, what about arbitrarily colored grids? Is the following general strategy still optimal?:

iterate over (x, y) in increasing order:
    if the 2 * 2 grid with (x, y) at the top left is all-white:
        color (x, y) black

One can prove that it indeed is (outline: the number of operations performed by any strategy cannot exceed the total number of 2 ∗22∗2 all-white subgrids in the initial grid (as upon every operation, one "converts" at least one 2 ∗22∗2 all-white sub-grid to non-all-white) and our strategy achieves exactly this upper bound).

So the answer to any query is just the number of 2 ∗22∗2 sub-grids that are initially all-white, which can be computed semi-naively in 𝑂(𝑞 ⋅𝑛)O(q⋅n) using per-row prefix sums.

B

This is my favorite problem from this contest.

We're given a complete undirected weighted graph where each edge has a weight of 00 or 11. We can perform operations of the following kind: we choose three nodes 𝑎,𝑏,𝑐a,b,c, and xor the weights of the three edges on the unique cycle between the three nodes with 11. What's the maximum number of edges with weight 11 that we can have after some (possibly empty) sequence of operations?

In problems like these (where we iteratively traverse between states towards some optimal endpoint), it helps to consider two things:

  • What an optimal state looks like (ie. its salient properties).
  • What invariants are maintained as we traverse between states.

Let's consider the optimal state. An observation that strikes one is that for any 33-cycle, at least 22 edges must have a weight of 11. Otherwise, we could just xor the cycle and get a strict increase in the score. This strict increase is important here, as it avoids any potential cyclicity between states.

Anyways, this implies that no node can have more than one incident edge with a weight of 00.

This nudges us in the direction of considering individual nodes. Notice that when we perform an operation on some cycle 𝑎,𝑏,𝑐a,b,c, the parity of the number of 11-weight edges incident to 𝑎a doesn't change. So for every node, we can deterministically check if it ends up with 00 or 11 edges of weight 11 in the optimal state (we just compare its initial parity with the parity of 𝑛 −1n−1, the degree of every node in the complete graph).

C

Maybe atcoder has changed over the past few years, because problems like these were only found in ABCs back in the good old days.

Let's divide segments 𝑠 →𝑡s→t into two kinds:

  • Type 1: 𝑠 <𝑡s<t
  • Type 2: 𝑡 <𝑠t<s

We quickly observe two conditions whose conjunction constitutes a necessary and sufficient condition for a solution to exist:

  1. No segments of different types can intersect.
  2. For any two segments of a common type, one cannot be completely contained within the other.

Note that the second condition implies that:

  1. For two type 11 segments 𝑠1 →𝑡1s1→t1 and 𝑠2 →𝑡2s2→t2, 𝑠1 <𝑠𝑡 ⟺ 𝑡1 <𝑡2s1<st⟺t1<t2.
  2. For two type 22 segments 𝑠1 →𝑡1s1→t1 and 𝑠2 →𝑡2s2→t2, 𝑠1 >𝑠𝑡 ⟺ 𝑡1 >𝑡2s1>st⟺t1>t2.

If the n&s conditions are satisfied, the following ordering is valid:

  1. First, we process all type 11 segments in decreasing order of 𝑠𝑖si.
  2. Then, we process all type 22 segments in increasing order of 𝑠𝑖si.

D

This is a much better problem than D, although it's also quite standard.

It can be reduced to the following:

Given a tree, find the maximum number of pairwise disjoint pairs of nodes (𝑥,𝑦)(x,y) such that lca⁡(𝑥,𝑦) ∉{𝑥,𝑦}lca⁡(x,y)∉{x,y}.

My path to the solution looked like the following:

  • Make some observations that would be instrumental to later proving why the solution I end up at works, but don't really advance my general intuition for the problem.
  • Draw on intuition from other problems to model a feasible solution.
  • Realize that the observations I made were actually useful if only I had thought about the problem in a different way.

An observation that we can make is that an optimal state is also maximal (ie. we cannot pair any nodes without having to break some existing pairs), so all the unpaired nodes lie on the path from the root to some leaf. I actually won't bother going into other details of this first phase.

Now, let's try using an idea that's fundamental to subtree-dp solutions here:

If you can compute the optimal answer for the subtree of node 𝑢u from the optimal answers for the subtrees of the children of 𝑢u, you can compute the answer for the root by going over nodes in a bottom-up manner.

Alright, so let's say that for some node 𝑢u, for every child 𝑐c, we've computed the number of unmatched nodes in the subtree of 𝑐c after optimally solving the matching problem for this subtree. How do we now optimally solve the matching problem for the subtree of 𝑢u?

Let's say the node 𝑢u had only two children 𝑐1c1 and 𝑐2c2. Some "greedy" steps that come to mind are:

  1. "Inter-match" the unmatched nodes between the subtrees of 𝑐1c1 and 𝑐2c2. This will result in only at most one subtree having some unmatched nodes.
  2. Assume that 𝑐1c1 still has some unmatched nodes. Then consider the pairs which have both nodes in the subtree of 𝑐2c2. If we have 2 unmatched nodes in the subtree of 𝑐1c1, we can simply break apart such a pair from 𝑐2c2, and match both the unmatched nodes from 𝑐1c1 with one of these newly unmatched nodes from 𝑐2c2. The number of times we do this is just min(𝑥/2,𝑦)min(x/2,y) where 𝑥x is the number of unmatched nodes in 𝑐1c1 and 𝑦y is the number of pairs completely contained within the subtree of 𝑐2c2.

It's easy to see that the above merging updates can be processed in 𝑂(1)O(1). For multiple children, when at some child 𝑣v, we can assume all the children we've processed before it to form a monolith that we consider to be 𝑐1c1, the current child to be 𝑐2c2, and just perform the same update.

E

My "solution" is just a naive brute-force:

  • Choose a block size 𝐵B and partition the array 𝑎a into blocks with this size.
  • Process elements in increasing order of 𝑖i. Whenever you enter a new block, recompute an SOS-DP array that includes all elements before this block.
  • To find the answer for some 𝑖i, you just consult one value in the SOS-DP array (corresponding to 𝑎𝑖ai), and also brute-force over all elements behind it in its own block.

This takes 𝑂((𝑛/𝐵) ⋅𝐿 ⋅2𝐿 +𝑛 ⋅𝐵)O((n/B)⋅L⋅2L+n⋅B) time, and can be made to pass with a not-terrible implementation and good block size.

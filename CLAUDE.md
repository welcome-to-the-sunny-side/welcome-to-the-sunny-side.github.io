# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

A static, terminal-driven personal website/blog: plain HTML pages generated by one Node script (`build.js`), a little vanilla JavaScript, Tailwind CSS, and an xterm.js terminal. Users navigate content via an in-browser terminal (ls, cd, open, pop, help) beside a content pane, or via breadcrumbs and index pages on mobile. Deployed to GitHub Pages at `www.welcome-to-the-sunny-side.com`.

`site-reference.md` documents every part of the site; consult it for implementation details and keep it updated when making changes.

## Commands

- `npm run build` — build to `dist/` (`node build.js`, ~4s)
- `npm run serve` — serve `dist/` at http://localhost:4321
- `npm run dev` — build + serve (no live reload; rebuild by hand)
- `npm run deploy` — build + push `dist/` to the gh-pages branch
- `node tools/shots.mjs capture <dir>` / `compare <a> <b>` — visual regression check (see site-reference.md §12). Run it before and after any change that could affect visuals; the goal is pixel-identical output.

## Architecture

**Content and VFS:** every file in `src/content/**/*.{md,html}` is a page; `.md` is shown as `.html`. Together they form the virtual file system the terminal browses (`src/build/vfs.js` scans it; the browser gets a compiled-in copy, `src/client/vfs.js`). Every directory gets a generated index page, so content may not be named `index.*`.

**Build:** `build.js` writes one static HTML file per page through the shell in `src/build/templates.js`, plus directory index pages, `site.css` (Tailwind via PostCSS, then esbuild), `js/` (esbuild bundle of `src/client/`), `/<path>.md` sources, `llms.txt` and `sitemap.xml`. `public/` is copied as is.

**Browser:** pages arrive complete and skinned. `src/client/site.js` is the entry point; `router.js` does client-side navigation by fetching the target's static HTML and swapping its `<main>`, breadcrumbs and head tags in, so the terminal survives and a page looks the same however it was reached. Don't add a second way of rendering a page on the client.

**Skins:** `dark` and `sunny` are CSS variables on `<html data-skin>` (`src/styles/skins.css`); Tailwind tokens map to them (`tailwind.config.js`), and skin-specific classes use the `dark:` variant (keyed on `[data-skin="dark"]`). An inline pre-paint script in `templates.js` applies the saved skin, terminal theme and collapsed state before first paint; `wearSkin()` in `src/client/skin.js` is the only other place that changes the skin. Terminal themes live in `src/client/terminalThemes.js`; `build.js` generates the pane's CSS from them.

## Key Details

- Tailwind only generates classes written out literally in `src/**/*.{js,html,md}`. Never build class names by string concatenation.
- Markdown rendering uses markdown-it + MathJax (math) + highlight.js (code). The renderer is a shared singleton in `src/lib/markdown.js` (used by the build and the musings page) — do not build a second markdown-it instance elsewhere.
- Math on markdown pages is typeset at **build time** (`src/build/typesetMath.js`). Client MathJax (CDN, `src/client/mathjax.js`) only runs for raw `.html` pages whose text contains math, the musings page, and re-breaking overflowing display equations (`rebreakDisplayMath`). Do not reintroduce whole-page client typesetting for markdown pages: it is what made math-heavy posts lag on mobile.
- Frontmatter is parsed by a tiny custom parser (`src/build/frontmatter.js`): `key: value`, quoted strings, one-line lists. That's all the content uses.
- Post figures are SVGs in `src/figures/`, inlined at build time by `src/build/figures.js` (placeholder: `<div class="svg-figure" data-svg="sais/x.svg" ...></div>`) and coloured per skin by their folder's `palette.css` (keyed on `<html data-skin>`), so they follow `cskin`. Keep figure colours out of `src/styles/skins.css`. Inlining must stay *after* `typesetMath` (MathJax would read `$` in figure text as math). Don't add skin-specific PNG figures.
- Raw `.html` content pages are inserted as they are (minus document-level tags). Their classic scripts re-run on every in-place visit; module scripts run once per page lifetime, so such a page should also do its work on the `site:load` event (as `src/client/musings.js` does).
- Below 768px the document scrolls; from 768px up `main` is the scroll container beside the terminal. This split is deliberate (iOS scroll lag on math-heavy posts); see site-reference.md §4.
- Global scale is set via `html { font-size }` in `global.css`; terminal font size is separate (`fontSize` in the xterm options in `src/client/terminal.js`).
- xterm.js measures its cell size once, at open: `mountTerminal` waits for IBM Plex Mono to load first. Keep that wait.
- xterm.js cursor movement escapes (`\x1b[D`, `\x1b[C`) don't wrap across visual rows. When fixing terminal input bugs at line boundaries, handle the boundary case specifically rather than rewriting the whole function.
- xterm.js `onKey` and `onData` fire alongside each other, not as alternatives. `preventDefault()` in `onKey` only stops browser defaults; the data callback still receives the keystroke. Escape sequences (Shift+Tab `\x1b[Z`, arrows `\x1b[A/B/C/D`) reach `writeChar` as data — the `escSeq` parser there is load-bearing, not dead code.

Suffix arrays in O(n) using SA-IS

Introduction

While the usual 𝑂(𝑛log⁡𝑛)O(nlog⁡n) suffix array algorithm described here suffices for almost all of one's competitive-programming needs, suffix structures turn out to be useful in several other fields which require faster algorithms. Lossless compression is one such field, and I happened to need a faster SA algorithm in an LZ-compressor I've been working on recently.

In this blog, we'll learn how to build suffix arrays in linear time, using the algorithm I learned for this purpose. It's called SA-IS ("Suffix Array by Induced Sorting", by Nong, Zhang, and Chan), and was originally described in this paper.

1. Preliminaries

We have a string 𝑇T of length 𝑛n.

For the sake of convenience:

  • We assume that 𝑇𝑖 ∈{1,2,…𝑛}Ti∈{1,2,…n} for all 𝑖 ∈[0,𝑛)i∈[0,n).
  • We add a unique sentinel element with value 00 at the end of 𝑇T. Note that this sentinel is the unique minimum in 𝑇T and the length now becomes 𝑛 +1n+1.
  • We define 𝑆𝑖Si to be the 𝑖i-th suffix, i.e. 𝑇𝑖𝑇𝑖+1…𝑇𝑛TiTi+1…Tn. At several places ahead, I will simply use "𝑖i-th suffix" or "suffix 𝑖i" to refer to 𝑆𝑖Si.

The goal is to construct the suffix array of 𝑇T in 𝑂(𝑛)O(n) time. The suffix array is defined as the array 𝐴A of length 𝑛 +1n+1, where 𝐴𝑖Ai corresponds to the index of the 𝑖i-th smallest suffix amongst all suffixes of 𝑇T (when compared lexicographically). One can note that the last character being unique ensures that no suffix is a prefix of another.

2. L and S-type suffixes

The key insight that SAIS is built around is that there's a lot of information hidden in comparisons of adjacent suffixes of a string (i.e. 𝑆𝑖Si vs 𝑆𝑖+1Si+1).

As such, we define two types of suffixes:

  1. Suffix 𝑖i is said to be of L-type, if 𝑖 <𝑛i<n and 𝑆𝑖 >𝑆𝑖+1Si>Si+1.
  2. Suffix 𝑖i is said to be of S-type, if 𝑖 =𝑛i=n or 𝑆𝑖 <𝑆𝑖+1Si<Si+1.

We will now make a series of observations about these two types in quick succession, so buckle up.

First, we characterise the structure of both types.

Theorem 2.1

Suffix 𝑖i is L-type iff 𝑖 <𝑛i<n and 𝑇𝑖 >𝑇𝑗Ti>Tj for the smallest 𝑗 ≥𝑖j≥i such that 𝑇𝑗 ≠𝑇𝑖Tj≠Ti.

Simply put, all L-type suffixes have the form [>= 1 occurrences of symbol b][1 occurrence of a]... where 𝑏 >𝑎b>a (𝑏b is the first character of the suffix here).

Proof

Let 𝑥 ≥0x≥0 be the smallest index where 𝑇𝑖+𝑥 ≠𝑇𝑖+1+𝑥Ti+x≠Ti+1+x. There must exist such an 𝑥x because the last element is unique. If 𝑖i is L-type, then we definitionally need 𝑇𝑖+𝑥 >𝑇𝑖+1+𝑥Ti+x>Ti+1+x (as 𝑆𝑖 >𝑆𝑖+1Si>Si+1). Therefore, we have 𝑇𝑖 =𝑇𝑖+𝑦Ti=Ti+y for all 0 ≤𝑦 ≤𝑥0≤y≤x and 𝑇𝑖 >𝑇𝑖+𝑥+1Ti>Ti+x+1.

Now, the other direction - if 𝑆𝑖Si takes the form [x >= 1 occurrences of b] [1 occurrence of a] where 𝑏 >𝑎b>a, then 𝑆𝑖 >𝑆𝑖+1Si>Si+1 because 𝑥x is the smallest non-negative integer where 𝑇𝑖+𝑥 ≠𝑇𝑖+1+𝑥Ti+x≠Ti+1+x, and we have 𝑇𝑖+𝑥 >𝑇𝑖+1+𝑥Ti+x>Ti+1+x.

Theorem 2.2

Suffix 𝑖i is S-type iff 𝑖 =𝑛i=n or 𝑇𝑗 >𝑇𝑖Tj>Ti for the smallest 𝑗 ≥𝑖j≥i such that 𝑇𝑗 ≠𝑇𝑖Tj≠Ti.

Simply put, all S-type suffixes, save for the sentinel, have the form [>= 1 occurrences of symbol b][1 occurrence of c]... where 𝑏 <𝑐b<c.

The proof is symmetrical to 2.1.

Theorem 2.3

All the positions in 𝑇T can be classified as L or S-type in 𝑂(𝑛)O(n).

Denote the type of the 𝑖i-th suffix by 𝑄𝑖Qi. Then:

  • 𝑄𝑛 =Qn= S-type.
  • For 𝑖 <𝑛i<n:
    • If 𝑇𝑖 <𝑇𝑖+1Ti<Ti+1, 𝑄𝑖Qi = S-type.
    • If 𝑇𝑖 >𝑇𝑖+1Ti>Ti+1, 𝑄𝑖Qi = L-type.
    • Else, 𝑄𝑖 =𝑄𝑖+1Qi=Qi+1.
Proof

We simply use 2.1 and 2.2 for all 𝑖 <𝑛i<n here:

  • If 𝑇𝑖 <𝑇𝑖+1Ti<Ti+1, then suffix 𝑖i is of the form b c ... where 𝑏 <𝑐b<c and therefore must be S-type.
  • If 𝑇𝑖 >𝑇𝑖+1Ti>Ti+1, then suffix 𝑖i is of the form b a ... where 𝑏 >𝑎b>a and therefore must be L-type.
  • If 𝑇𝑖 ==𝑇𝑖+1Ti==Ti+1, then suffix 𝑖 +1i+1 is either of the form [>= 1 occurrences of b][1 occurrence of a]... or [>= 1 occurrences of b][1 occurrence of c]..., and this determines its type. If we prepend one b to either form (𝑆𝑖 =𝑏𝑆𝑖+1Si=bSi+1), then the form doesn't change and neither does the type.

Theorem 2.4

If 𝑇𝑖 =𝑇𝑗Ti=Tj, suffix 𝑖i is of L-type, and suffix 𝑗j is of S-type, then 𝑆𝑖 <𝑆𝑗Si<Sj.

Proof

𝑆𝑖Si has the form [>= 1 occurrences of b] [1 occurrence of a]... and 𝑆𝑗Sj has the form [>= 1 occurrences of b][1 occurrence of c].... It's easy to see that at the smallest 𝑥 ≥0x≥0 where 𝑇𝑖+𝑥 ≠𝑇𝑗+𝑥Ti+x≠Tj+x, we have one of the following:

  • 𝑇𝑖+𝑥 =𝑏,𝑇𝑗+𝑥 =𝑐Ti+x=b,Tj+x=c
  • 𝑇𝑖+𝑥 =𝑎,𝑇𝑗+𝑥 =𝑏Ti+x=a,Tj+x=b
  • 𝑇𝑖+𝑥 =𝑎,𝑇𝑗+𝑥 =𝑐Ti+x=a,Tj+x=c

In every case, we have 𝑇𝑖+𝑥 <𝑇𝑗+𝑥Ti+x<Tj+x, and therefore 𝑆𝑖 <𝑆𝑗Si<Sj.

Now, theorem 2.4 is quite powerful as it allows us to characterise the structure of the suffix array in a very friendly "bucketed" manner. We can observe that the suffix array must take the following form:

  • First, we have L-type suffixes that start with symbol 00.
  • Then, we have S-type suffixes that start with symbol 00.
  • Then, L-type suffixes that start with symbol 11.
  • Then, S-type suffixes that start with symbol 11.
  • Then, L-type suffixes that start with symbol 22.
  • Then, S-type suffixes that start with symbol 22.
  • ...and so on

In other words:

  • The suffix array consists of several disjoint buckets, with each bucket corresponding to suffixes starting with a certain symbol.
  • The buckets are ordered by the starting symbol.
  • Within a particular bucket, we first have all the L-type suffixes, and then all the S-type suffixes.

It's easy to see that these bucket boundaries can also be computed in 𝑂(𝑛)O(n). It might seem odd that I'm mentioning this, but it's important for the implementation later.

Code 
// Given n and T
int n;
vector<int> T;

vector<int> cnt(n + 1, 0);
for(auto x : T)
    cnt[x]++;

auto tail = cnt;
for(int i = 1; i <= n; i++)
    tail[i] += tail[i - 1];

auto head = tail;
for(int i = 0; i <= n; i ++)
    head[i] -= cnt[i];

//now, bucket for element i is [head[i], tail[i])

3. LMS-types

We define a suffix 𝑖i to be of LMS-type (i.e. "Leftmost-S-type") iff:

  • 𝑖 >0i>0
  • Suffix 𝑖i is of S-type.
  • Suffix 𝑖 −1i−1 is of L-type.

Let 𝑙0 <𝑙1 <⋯ <𝑙𝑚−1l0<l1<⋯<lm−1 be the LMS positions of 𝑇T.

A key observation is that there are 𝑚 ≤𝑛+12m≤n+12 LMS positions (the existence of each LMS position "consumes" a unique L-type and S-type). As you will later see, the efficiency of SAIS is dependent on this.

Theorem 3.1

If 𝑖i is LMS-type, then 𝑇𝑖−1 >𝑇𝑖Ti−1>Ti.

Proof

If 𝑖i is LMS, then 𝑖 >0i>0 and 𝑖 −1i−1 is L-type. By theorem 2.3, we cannot have 𝑇𝑖−1 ≤𝑇𝑖Ti−1≤Ti because then 𝑖 −1i−1 would have been S-type.

Now, let's introduce a very helpful visualisation for strings that I'll just call a "slope view". The slope view of any given string will be obtained by us drawing downward or upward slants between two adjacent suffixes based on the result of their comparison (i.e. the type of the left suffix).

Let's look at some visualisations for 𝑇 =T= baacbcbacbccdaa$ (where $ is the appended unique minimum). I know I said that 𝑇T will have integer elements, but an english alphabet string is just nicer to look at, and is no different computationally (just assign some integer to every letter).

A few observations:

  • LMS-types correspond to valleys in the slope view.
  • An upward slope (from left to right) corresponds to S-type suffixes.
  • A downward slope corresponds to L-type suffixes.
  • The second-last character is always L-type, as the last character is the unique minimum. Since the last position is definitionally S-type, this also implies that it's always LMS-type.

4. Induced sorting

Now, after having tunnel-visioned on the classification of these L/S types for so long, let's return to our original goal of finding 𝐴A. Why did we do all of this? As it turns out, it's really convenient to sort L-suffixes and S-suffixes separately.

4.1 L-induce

Say we were tasked with producing 𝐴A partially, i.e. only at positions 𝑖i such that 𝐴𝑖Ai was an L-type position. Does the problem get meaningfully easier?

The observation that the entire algorithm is built upon is that we don't need any S-type suffixes except the LMS-types to induce the sorted order of L-type suffixes.

Theorem 4.1

Given the sorted order of LMS-suffixes (a permutation 𝐺G of 𝑙0,𝑙1…𝑙𝑚−1l0,l1…lm−1 where 𝑆𝐺𝑖 <𝑆𝐺𝑖+1SGi<SGi+1 for 𝑖 +1 <𝑚i+1<m), we can compute in 𝑂(𝑛)O(n) time all 𝐴𝑖Ai where 𝐴𝑖Ai is an L-type position. Less formally, we can fill out all the "L-buckets" of 𝐴A in 𝑂(𝑛)O(n) time.

The rest of subsection 4.1 will be spent realising an algorithm which does this.

Let's first consider a really inefficient procedure to sort L-type suffixes while only making use of LMS-types (besides the L-types). This is really the sort of algorithm where it's simpler to use an unambiguous, real programming language rather than pseudocode, so you'll have to bear with C++ snippets throughout.

Procedure 1 
// Given n, T, S, bucket boundaries (see code in theorem 2.4)
int n;
vector<int> T, head, tail;
vector<vector<int>> S;          //suffixes

vector<int> A(n + 1, -1);

set<pair<vector<int>, int>> q;

auto extend = [&](int i) -> void
{
    int j = i - 1;
    if(j >= 0 and is_L_type(j))
        q.insert({S[j], j});
};

for(int i = 0; i <= n; i ++)
    if(is_LMS_type(i))
        q.insert({S[i], i});

while(!q.empty())
{
    auto [v, i] = *q.begin();
    q.erase(q.begin());

    //we do not place the LMS types into A
    if(is_L_type(i))
    {
        A[head[T[i]]] = i;
        head[T[i]] ++;
    }

    extend(i);
}

This inefficient procedure essentially does the following:

  1. It first inserts all the LMS-suffixes into a heap (that uses the standard lexicographical comparator).
  2. Then, it repeatedly picks and deletes the smallest suffix from the heap and:
    1. If the suffix corresponds to an L-type position 𝑖i, it places 𝑖i at the first free position in the L-bucket corresponding to 𝑇𝑖Ti in 𝐴A.
    2. Then, if position 𝑖 −1i−1 is L-type, it inserts 𝑆𝑖−1Si−1 into the heap (i.e. it extends the removed suffix by one character on the left, or equivalently in the slope-view - moves one step up to the left).

Before we prove that this procedure is correct, I encourage you to intuit why this is correct by visualising the slope view.

Intuition

We essentially "seed" the heap by inserting all the valley positions, and then inch up each L-type slope to the left (remember, L-type slopes slant upwards from right to left). Alternatively, you can think of it this way - imagine every upward (right to left) slope of consecutive L-types to be an increasing array. The suffix array is constructed by interleaving all of these into one big increasing array where all the arrays exist as disjoint increasing subsequences. Then we're simply using the heap to help us do this interleaving - we start off by inserting the smallest (first) element from every array into the heap, and then we always delete the smallest element from it. Also, whenever we delete an element from the heap, we insert the next element from that element's array into the heap.

Anyway, how do we formally prove correctness?

Notice that when suffix 𝑆𝑖Si is deleted from the heap, it can only result in the insertion of a strictly greater suffix back into the heap (𝑆𝑖−1Si−1, where 𝑖 −1i−1 must be L-type, so 𝑆𝑖−1 >𝑆𝑖Si−1>Si. In the slope view, 𝑖 −1i−1 must be above 𝑖i). Since we always delete the smallest suffix from the heap, this implies that all suffixes to ever be inserted in the heap are deleted in non-decreasing order (for any two L or LMS-type positions 𝑖i and 𝑗j, if 𝑆𝑖 <𝑆𝑗Si<Sj, then 𝑖i is deleted from the heap before 𝑗j).

Now consider the manner in which we insert elements into 𝐴A. It's easy to see that every suffix 𝑖i is guaranteed to be placed somewhere within the L-bucket of 𝑖i. Within every L-bucket, suffixes are placed correctly too, as they were deleted in non-decreasing order from the heap, and therefore placed into the L-bucket in the same order.

What about coverage? Does every L-type position eventually get placed into 𝐴A? Yes! Remember that the last element is always LMS-type (a valley), and therefore, every L-type position has an LMS-type position somewhere after it (more formally, every L-type position has either an L-type position or LMS-type position to its right).

Now, we make a subtle modification to this procedure that preserves correctness, but allows us to later optimise it. Consider the following:

Procedure 2 
// Given n, T, S, bucket boundaries (see code in theorem 2.4)
int n;
vector<int> T, head, tail;
vector<vector<int>> S;          //suffixes

vector<int> A(n + 1, -1);       //suffix array

set<pair<vector<int>, int>> q;

auto extend2 = [&](int i) -> void
{
    int j = i - 1;
    if(j >= 0 and is_L_type(j))
    {
        A[head[T[j]]] = j;
        head[T[j]] ++;
        q.insert({S[j], j});
    }
};

for(int i = 0; i <= n; i ++)
    if(is_LMS_type(i))
        q.insert({S[i], i});

while(!q.empty())
{
    auto [v, i] = *q.begin();
    q.erase(q.begin());

    extend2(i);
}

What changed? Instead of placing L-type 𝑖i into 𝐴A when 𝑆𝑖Si gets deleted from the heap, we place 𝑖i into 𝐴A when it gets inserted into the heap. When does it get inserted into the heap? When 𝑆𝑖+1Si+1 is deleted.

Why is this procedure correct? First, observe that elements are still deleted from the heap in non-decreasing order.

All L-type positions are necessarily placed within their buckets in 𝐴A, so for any two L-type positions 𝑖i and 𝑗j with 𝑇𝑖 <𝑇𝑗Ti<Tj, 𝑖i will necessarily be placed before 𝑗j in 𝐴A. Therefore, we need only show that the relative placement of L-type positions within buckets is correct.

Consider any two L-type positions 𝑖i and 𝑗j with 𝑇𝑖 =𝑇𝑗 =𝑐Ti=Tj=c. Since 𝑇𝑖 =𝑇𝑗Ti=Tj, 𝑆𝑖 <𝑆𝑗 ⟺ 𝑆𝑖+1 <𝑆𝑗+1Si<Sj⟺Si+1<Sj+1. But recall that elements are still deleted from the heap in non-decreasing order! Since 𝑖i and 𝑗j are L-type, 𝑖 +1i+1 and 𝑗 +1j+1 are L or LMS-type, and pass through the heap before 𝑖i and 𝑗j respectively (𝑆𝑖 >𝑆𝑖+1Si>Si+1 and 𝑆𝑗 >𝑆𝑗+1Sj>Sj+1). Assume WLOG 𝑆𝑖+1 <𝑆𝑗+1Si+1<Sj+1. But then, 𝑆𝑖+1Si+1 is deleted before 𝑆𝑗+1Sj+1, and 𝑖i is placed in the L-bucket of 𝑐c before 𝑗j, just like we require. Therefore, suffixes are placed in the correct order within buckets.

This proves that the L-regions of 𝐴A are correctly filled by this procedure too.

Notice that our proof only relied on suffixes being deleted from the heap in non-decreasing order.

Theorem 4.2

Sequentially calling extend2(i) on some non-decreasing sequence of suffixes 𝑖1,𝑖2,𝑖3,…i1,i2,i3,… which contains all L/LMS-type positions exactly once results in the L-regions of 𝐴A being correctly filled.

Now, how can we do this faster?

First, we divorce extend2(i) from the heap. From this point onward, it will no longer add anything to the heap.

Let's make use of Theorem 4.2. Imagine that we had access to some pre-built, valid 𝐴′A′. We could then simply call extend2(A'[i]) in increasing order of 𝑖i, where 𝐴′𝑖Ai′ was L or LMS-type. Alas, we do not have access to a pre-built 𝐴′A′... But we notice that calling extend2(A'[i]) only possibly places an element into 𝐴A to the right of 𝑖i (so as we walk from left to right, we only place elements to our right, and there are no "circular dependencies").

What if we could do the following at the same time?:

  • Build 𝐴A.
  • Use 𝐴A itself as a pre-built 𝐴′A′ that we walk from left to right and call extend2(A'[i]) on?

Effectively (and I switch to pseudo-code now):

A = [-1] * (n + 1)
for i from 0 to n:
    if (A[i] != -1) and (A[i] is L or LMS type):
        extend2(A[i])

This is of course incorrect, for the simple reason that everything remains -1, but the fix is smaller than you might expect.

The problem is illustrated well by considering this procedure's equivalence to procedure 2. Remember that we delete suffixes 𝑆𝑖Si in non-decreasing order. This effectively means that the position of 𝑆𝑖Si in 𝐴A keeps increasing as time goes on, and the deletion order can be grouped like this:

  • First, we delete all indices in the L-bucket of 00 (L-suffixes that begin with 00).
  • Then, LMS indices in the S-bucket of 00.
  • Then, all indices in the L-bucket of 11.
  • Then, LMS indices in the S-bucket of 11
  • and so on

The issue here is that while we don't need the heap at all to handle the L-regions, it's doing critical work for us in the S-regions.

In particular, we can already modify procedure 2 to run in linear time for the L-regions in the following manner:

Procedure 2.5 
A = [-1] * (n + 1)

put {S[i], i} for all LMS-type i into heap H

# we iterate over the first character of suffixes
for character c from 0 to n:

    # we first process the L-region of c
    let A[l, r] be the L-region for c
    for i from l to r:
        extend2(A[i])
  
    # we then process the LMS-types of c, naively
    while H is not empty and the smallest suffix in H begins with c:
        pop out {S[i], i}, the smallest element of H
        extend2(i)

Why is this correct? Because extend2(i) is called on exactly the same sequence of 𝑖i in both, procedure 2 and 2.5.

Annoying Proof

We can prove this using induction. Assume that the first 𝑘k calls to extend2() are made on the exact same sequence of indices in both procedures. Then let the 𝑘 +1k+1-th call in procedure 2 be on index 𝑖i.

  1. If 𝑖i is LMS type: Suffix 𝑖i is then present within both heaps from the very beginning. We will make use of the fact that no two suffixes can be equal. Procedure 2 would have already deleted all strings strictly smaller than it from the heap (remember that it calls extend2() in strictly increasing order of suffixes), and since 2.5 also called extend2() for the same indices, it would also have deleted all suffixes smaller than 𝑆𝑖Si from its own heap. Therefore, at this point of time 𝑆𝑖Si must be the smallest string in procedure 2.5's heap, and we will pop it out now.
  2. If 𝑖i is L-type: Then it will be placed somewhere in the L-region of 𝑇𝑖Ti. Notice that its position in both procedures is determined solely by the number of times we call extend2(j) for 𝑗j such that 𝑗 >0,𝑄𝑗−1 =L,𝑇𝑗−1 =𝑇𝑖j>0,Qj−1=L,Tj−1=Ti before we call extend2(i + 1). All of these calls lie within the first 𝑘k calls (𝑖i is L-type so 𝑆𝑖 >𝑆𝑖+1Si>Si+1), and are therefore the same for both procedures, implying that 𝑖i gets placed at the same position in both.

Looking at the second stage for each 𝑐c, it's easy to see that the heap was only really responsible for sorting the LMS-suffixes (all insertions are before all deletions now, so we don't need its "online" nature, we just need the sorted order of all LMS suffixes). This brings us back to theorem 4.1. We don't really need the entirety of a pre-built 𝐴′A′ - we only need 𝐺G!

Let's finally look at the L-induce procedure, which takes 𝐺G and computes the L-regions of 𝐴A. An implementation choice here is that since the S-regions of 𝐴A are otherwise unused during this phase, we just put all LMS positions from the given 𝐺G at the ends of their respective S-buckets in 𝐴A, preserving their order.

Procedure 3 
// Given n, T, and the bucket boundaries (see code in theorem 2.4)
int n;
vector<int> T, head, tail;

// Of course, given G too!
vector<int> G;

vector<int> A(n + 1, -1);       //suffix array

// Seeding - we put LMS positions at the tails of their S-buckets 
reverse(G.begin(), G.end());
for(auto i : G)
    A[--tail[T[i]]] = i;

auto extend2 = [&](int i) -> void
{
    int j = i - 1;
    if(j >= 0 and is_L_type(j))
    {
        A[head[T[j]]] = j;
        head[T[j]] ++;
    }
};

// induce L positions into A
auto l_induce = [&]() -> void
{
    for(int i = 0; i <= n; i ++)
        if(A[i] != -1)
            extend2(A[i]);
};
l_induce();

// clean up LMS types from A
for(int i = 0; i <= n; i ++)
    if(A[i] != -1 and is_LMS_type(A[i]))
        A[i] = -1;

It's easy to see that this procedure is correct (it's just the previous procedure with the second stage for each 𝑐c made efficient), and that apart from the magical acquisition of 𝐺G, it runs in 𝑂(𝑛)O(n) (placing LMS-positions into 𝐴A, L-induce itself, cleanup).

4.2 S-induce

Let us now deal with the S regions.

The basic idea is symmetrical - just like we processed L-suffixes in non-decreasing order to fill the L-regions (left to right in 𝐴A), we will process S-suffixes in non-increasing order to fill the S-regions (right to left). In the slope view, we previously inched upwards on slopes that were slanted upward from right to left, after having seeded the valleys (𝐺G). Now, we will inch downwards on slopes that are slanted downward from right to left (remember the slant of slopes for S-suffixes). We have an advantage here though! The analogous seeds are going to be the "leftmost L" (LML) positions (peaks in the slope view), which lie in the L-regions of 𝐴A. Since we have already computed the L-regions, we already have the analogue of 𝐺G here!

Anyway, let's look at the procedure and then talk about it:

Procedure 4 
// Given n, T, bucket boundaries, and A with L-regions computed
// Note that these are freshly computed bucket boundaries, not those
// modified in the L phase. 
int n;
vector<int> T, head, tail, A;

auto extend3 = [&](int i) -> void
{
    int j = i - 1;
    if(j >= 0 and is_S_type(j))
    {
        tail[T[j]] --;
        A[tail[T[j]]] = j;
    }
};

// place the sentinel position separately
A[0] = n;

// induce S positions into A
auto s_induce = [&]() -> void
{
    for(int i = n; i >= 0; i --)
        if(A[i] != -1)
            extend3(A[i]);
};
s_induce();

Why does this work? The proof is structurally symmetric to that of L-induce (we now process strings in non-increasing order, so we go from right to left in 𝐴A, and every call to extend3(A[i]) can only add something to 𝐴A strictly before 𝑖i), but with one caveat: coverage previously relied on the fact that every sequence of L positions ended in an LMS position (every downward slope ends in a valley), and us manually placing the LMS positions into 𝐴A first. The equivalent requirement here would be every upward slope ending in a peak, and us having placed every peak first. As all L regions have already been computed, all the peaks have been placed into 𝐴A. The only source of nuisance is the very last position, which is LMS-type and doesn't have an L-type peak after it.

Thankfully:

  • 𝑇𝑛Tn is the unique minimum and must therefore be the very first element in 𝐴A, so we manually place it.
  • Because it's the unique minimum, 𝑛 −1n−1 is L-type. Therefore, all other S-type positions have some peak after them (a "Leftmost L type").

I leave the formal proof of correctness to the reader, and return to the broader picture.

We now know that just having 𝐺G would allow us to set off a convenient chain of events (the induction phases) which would end in 𝑂(𝑛)O(n) time, with us having computed 𝐴A. The entire problem therefore reduces to being able to sort the LMS-suffixes efficiently.

5. Sorting LMS-suffixes

Okay, so how do we sort LMS suffixes efficiently? The S induce would of course give us their sorted order, but that needs the L induce, which needs the sorted order... It's a bit of a chicken-and-egg problem.

Let's think outside the box. The observant reader will remember that the number of LMS positions, 𝑚m is no more than 𝑛+12n+12. What if we could somehow "compress" 𝑇T to 𝑇′T′ of length 𝑚m, where the 𝑖i-th suffix of 𝑇′T′ corresponded to 𝑆𝑙𝑖Sli, and the sorted order of the suffixes of 𝑇′T′ gave us the sorted order of the corresponding LMS-suffixes of 𝑇T (that is, the 𝑖i-th suffix of 𝑇′T′ is smaller than the 𝑗j-th, iff 𝑆𝑙𝑖 <𝑆𝑙𝑗Sli<Slj)? If we could create such a 𝑇′T′, then finding its suffix array would just be an identical subproblem to our original task, but with smaller size!

Let's imagine a magical procedure compress(T) which gives us such a 𝑇′T′ in linear time. Then we can define SA(T), which computes the SA of 𝑇T (assuming that 𝑇T satisfies the conditions in section 1) in the following manner:

#input T satisfies properties from section 1
SA(T):
    N = |T|

    #base case
    if N == 1:
        return [0]

    T2 = compress(T)

    G = SA(T2)
    for i from 0 to |G| - 1:
        G[i] = l[G[i]]    #G[i]-th LMS position in T

    A = [-1] * (N)
    run L induce on A using G
    run S induce

    return A

What would the time complexity of SA(T), 𝑓(𝑁)f(N) (𝑁 =|𝑇|N=|T|) be? We have 𝑓(𝑁) =𝑂(𝑁) +𝑓(𝑁/2) +𝑂(𝑁) +𝑂(𝑁) +𝑂(𝑁)f(N)=O(N)+f(N/2)+O(N)+O(N)+O(N) (the recursive call takes 𝑓(𝑁/2)f(N/2) time, and every other phase takes linear time). Therefore, 𝑓(𝑁) =𝑂(𝑁) +𝑓(𝑁/2)f(N)=O(N)+f(N/2). Also, the base case is handled with 𝑓(1) =𝑂(1)f(1)=O(1). Since 𝑂(𝑁) +𝑂(𝑁/2) +𝑂(𝑁/4) +⋯ =𝑂(𝑁)O(N)+O(N/2)+O(N/4)+⋯=O(N), we have 𝑓(𝑁) =𝑂(𝑁)f(N)=O(N).

All that remains is to design such a compress(T).

Since the 𝑖i-th suffix of 𝑇′T′ = compress(T) is going to correspond to the 𝑖i-th LMS suffix of 𝑇T (which starts with 𝑙𝑖li), it should be reasonably intuitive that we try to assign 𝑇′𝑖Ti′ a symbol that somehow represents the substring from the 𝑖i-th LMS position to the (𝑖 +1)(i+1)-th (or if 𝑖 =𝑚 −1i=m−1, the end of the string). Note that choosing this particular substring to be represented by 𝑇′𝑖Ti′ is only a design choice here.

5.1 LMS Substrings

We define the LMS-end of position 𝑖i, 𝐸𝑖Ei, as the smallest LMS-position such that 𝑖 <𝐸𝑖i<Ei. For 𝑖 =𝑛i=n, we separately define 𝐸𝑖 =𝑖Ei=i. The LMS-substring of position 𝑖i, 𝑃𝑖Pi is defined as 𝑇[𝑖,𝐸𝑖]T[i,Ei]. Additionally, we refer to 𝑃𝑖Pi as a "full" LMS-substring if 𝑖i is LMS-type.

Now, return to compress(T). We wish to find a labelling function 𝑅 :{𝑃𝑖} →𝑍R:{Pi}→Z that will assign an integer label to each full LMS-substring such that the resultant string, 𝑇′T′ (𝑇′𝑖 =𝑅(𝑃𝑙𝑖)Ti′=R(Pli)) meets the following conditions:

  1. 𝑇′𝑖Ti′ is an integer in [0,|𝑇′|)[0,|T′|)
  2. The last element of 𝑇′T′ is the unique minimum.
  3. The 𝑖i-th suffix of 𝑇′T′ is smaller than the 𝑗j-th, iff 𝑆𝑙𝑖 <𝑆𝑙𝑗Sli<Slj.

To recap, why do we need these conditions? The first and second are needed so that 𝑇′ =T′= compress(T) can directly be passed to SA(T) (which assumes that the conditions from section 1 are met). The third is needed so that 𝐺G can be computed from the suffix array of 𝑇′T′.

The first and second conditions are relatively simple to satisfy, but the third isn't. A condition on 𝑅R that naively seems helpful for the third is 𝑅(𝑃𝑖) <𝑅(𝑃𝑗) ⟺ 𝑃𝑖 <𝑃𝑗R(Pi)<R(Pj)⟺Pi<Pj, let's try to build 𝑅R around it.

Consider the labelling function: 𝑅(𝑃𝑖) =|{𝑃𝑗 :𝑃𝑗 <𝑃𝑖,𝑄𝑗 =LMS}|R(Pi)=|{Pj:Pj<Pi,Qj=LMS}| (the number of unique full LMS substrings that are strictly smaller than it). It trivially satisfies the first two conditions, but what about the third?

Let's compare the 𝑖i-th and 𝑗j-th suffixes of 𝑇′T′.

  • Since the last character of 𝑇′T′ is the unique minimum, no suffix of 𝑇′T′ can be a proper prefix of another suffix.
  • Therefore, consider the smallest 𝑥 ≥0x≥0 such that 𝑇′𝑖+𝑥 ≠𝑇′𝑗+𝑥Ti+x′≠Tj+x′. Clearly 𝑇′[𝑖,𝑚) <𝑇′[𝑗,𝑚) ⟺ 𝑇′𝑖+𝑥 <𝑇′𝑗+𝑥T′[i,m)<T′[j,m)⟺Ti+x′<Tj+x′.
  • Let 𝑢 =𝑙𝑖+𝑥,𝑣 =𝑙𝑗+𝑥u=li+x,v=lj+x. Since 𝑇′[𝑖,𝑖 +𝑥 −1] =𝑇′[𝑗,𝑗 +𝑥 −1]T′[i,i+x−1]=T′[j,j+x−1], we have 𝑇[𝑙𝑖,𝑢) =𝑇[𝑙𝑗,𝑣)T[li,u)=T[lj,v) (easy to prove, left as an exercise). Now, 𝑇[𝑙𝑖,𝑛] <𝑇[𝑙𝑗,𝑛] ⟺ 𝑇[𝑢,𝑛] <𝑇[𝑣,𝑛]T[li,n]<T[lj,n]⟺T[u,n]<T[v,n].
  • We know that 𝑃𝑢 ≠𝑃𝑣Pu≠Pv (𝑇′𝑖+𝑥 ≠𝑇′𝑗+𝑥Ti+x′≠Tj+x′). There are two cases:
    • If neither 𝑃𝑢Pu nor 𝑃𝑣Pv is a proper prefix of the other, then 𝑇[𝑢,𝑛] <𝑇[𝑣,𝑛] ⟺ 𝑃𝑢 <𝑃𝑣 ⟺ 𝑅(𝑃𝑢) <𝑅(𝑃𝑣) ⟺ 𝑇′𝑖+𝑥 <𝑇′𝑗+𝑥T[u,n]<T[v,n]⟺Pu<Pv⟺R(Pu)<R(Pv)⟺Ti+x′<Tj+x′! Therefore, in this case, we have 𝑇′[𝑖,𝑚) <𝑇′[𝑗,𝑚) ⟺ 𝑇[𝑙𝑖,𝑛] <𝑇[𝑙𝑗,𝑛]T′[i,m)<T′[j,m)⟺T[li,n]<T[lj,n].
    • Otherwise, WLOG assume 𝑃𝑢Pu is a proper prefix of 𝑃𝑣Pv. In this case, the lex comparator says 𝑃𝑢 <𝑃𝑣 ⟹ 𝑅(𝑃𝑢) <𝑅(𝑃𝑣) ⟹ 𝑇′𝑖+𝑥 <𝑇′𝑗+𝑥 ⟹ 𝑇′[𝑖,𝑚) <𝑇′[𝑗,𝑚)Pu<Pv⟹R(Pu)<R(Pv)⟹Ti+x′<Tj+x′⟹T′[i,m)<T′[j,m). For 𝑇′[𝑖,𝑚) <𝑇′[𝑗,𝑚) ⟺ 𝑇[𝑙𝑖,𝑛] <𝑇[𝑙𝑗,𝑛]T′[i,m)<T′[j,m)⟺T[li,n]<T[lj,n] to now be satisfied, we need 𝑇[𝑙𝑖,𝑛] <𝑇[𝑙𝑗,𝑛]T[li,n]<T[lj,n]. Let's examine this in more detail.

Surprisingly, properties of the L/S classification trivialise this. Let 𝑝 =|𝑃𝑢|p=|Pu|. Notice that 𝑃𝑢 =𝑇[𝑢,𝑢 +𝑝 −1] =𝑇[𝑣,𝑣 +𝑝 −1]Pu=T[u,u+p−1]=T[v,v+p−1], so 𝑇[𝑙𝑖,𝑛] <𝑇[𝑙𝑗,𝑛] ⟺ 𝑇[𝑢 +𝑝 −1,𝑛] <𝑇[𝑣 +𝑝 −1,𝑛]T[li,n]<T[lj,n]⟺T[u+p−1,n]<T[v+p−1,n]. We know that 𝑇𝑢+𝑝−1 =𝑇𝑣+𝑝−1Tu+p−1=Tv+p−1 and position (𝑢 +𝑝 −1)(u+p−1) is LMS-type (it's the end of an LMS-substring). What about position 𝑣 +𝑝 −1v+p−1? Using theorem 3.1, 𝑇𝑢+𝑝−2 >𝑇𝑢+𝑝−1 ⟹ 𝑇𝑣+𝑝−2 >𝑇𝑣+𝑝−1Tu+p−2>Tu+p−1⟹Tv+p−2>Tv+p−1, so position 𝑣 +𝑝 −2v+p−2 must be L-type. Recall that the types of positions in an LMS substring take the following form: LMS S S S S ... L L L L LMS. Since 𝑃𝑣Pv doesn't end at 𝑣 +𝑝 −1v+p−1, position 𝑣 +𝑝 −1v+p−1 must be L-type too!

Recall theorem 2.4! Since 𝑆𝑢+𝑝−1Su+p−1 and 𝑆𝑣+𝑝−1Sv+p−1 begin with the same character, and the former is S-type while the latter is L-type, we must have 𝑇[𝑢 +𝑝 −1,𝑛] >𝑇[𝑣 +𝑝 −1,𝑛] ⟹ 𝑇[𝑙𝑖,𝑛] >𝑇[𝑙𝑗,𝑛]T[u+p−1,n]>T[v+p−1,n]⟹T[li,n]>T[lj,n]! which is... the exact opposite of what we wanted. But since the issue is so localised (i.e. in the comparison of full LMS substrings where one is a proper prefix of the other), could we make do with a localised fix?

We indeed can! We introduce the alex comparator, ≺≺. For strings 𝑎a and 𝑏b, it is defined in the following manner:

  • If 𝑎 =𝑏a=b under lex, then they're equal under alex too.
  • Otherwise if neither 𝑎a nor 𝑏b is a proper prefix of the other, then 𝑎 ≺𝑏 ⟺ 𝑎 <𝑏a≺b⟺a<b.
  • Otherwise, 𝑎 ≺𝑏 ⟺ |𝑎| >|𝑏|a≺b⟺|a|>|b|.

Simply put, it's just the standard lexicographical comparator, except we flip the comparison result when one string is a proper prefix of the other.

Also, we can show that alex imposes a total order. Why? Because 𝐴 ≺𝐵 ⟺ 𝐴∞ <𝐵∞A≺B⟺A∞<B∞ and 𝐴 =𝐵 ⟺ 𝐴∞ =𝐵∞A=B⟺A∞=B∞. That is, the result of alex comparison is equal to the result of lex comparison if you append a character that's larger than all others to the end of both strings. Since lex imposes a total order, alex does too.

Redefine 𝑅R as 𝑅(𝑃𝑖) =|{𝑃𝑗 :𝑃𝑗 ≺𝑃𝑖,𝑄𝑗 =LMS}|R(Pi)=|{Pj:Pj≺Pi,Qj=LMS}|, and recall the three required conditions on 𝑅R:

  1. 𝑇′𝑖Ti′ is an integer in [0,|𝑇′|)[0,|T′|) - trivially satisfied.
  2. The last element of 𝑇′T′ is the unique minimum - satisfied because 𝑃𝑙𝑚−1Plm−1 remains the unique minimum amongst all full LMS substrings, so 𝑅(𝑃𝑙𝑚−1) =0R(Plm−1)=0.
  3. The 𝑖i-th suffix of 𝑇′T′ is smaller than the 𝑗j-th, iff 𝑆𝑙𝑖 <𝑆𝑙𝑗Sli<Slj.

Consider the third condition. When we previously attempted to prove 𝑇′[𝑖,𝑚) <𝑇′[𝑗,𝑚) ⟺ 𝑇[𝑙𝑖,𝑛] <𝑇[𝑙𝑗,𝑛]T′[i,m)<T′[j,m)⟺T[li,n]<T[lj,n] for 𝑇′T′ defined using the old definition of 𝑅R (using the regular lex comparator), there were only four relevant properties:

  • For character 𝑐c, and strings 𝐴A and 𝐵B, 𝑐𝐴 <𝑐𝐵 ⟺ 𝐴 <𝐵cA<cB⟺A<B, and 𝑐𝐴 =𝑐𝐵 ⟺ 𝐴 =𝐵cA=cB⟺A=B.
  • For full LMS substrings 𝐴A and 𝐵B:
    • If neither was a prefix of the other, 𝑅(𝐴) <𝑅(𝐵) ⟺ 𝐴 <𝐵R(A)<R(B)⟺A<B.
    • 𝑅(𝐴) =𝑅(𝐵) ⟺ 𝐴 =𝐵R(A)=R(B)⟺A=B.
    • When 𝐴A is a proper prefix of 𝐵B, we required 𝑅(𝐴) >𝑅(𝐵)R(A)>R(B), but our old 𝑅R yielded 𝑅(𝐴) <𝑅(𝐵)R(A)<R(B).

Clearly, our new definition of 𝑅R satisfies all four! I won't restate the entire proof again, but encourage you to go through the argument again to convince yourself of this.

5.2 Sorting LMS Substrings under alex

Okay, so we've finally found a suitable definition for 𝑅R - 𝑅(𝑃𝑖) =|{𝑃𝑗 :𝑃𝑗 ≺𝑃𝑖,𝑄𝑗 =LMS}|R(Pi)=|{Pj:Pj≺Pi,Qj=LMS}| where ≺≺ is the alex comparator. But how do we efficiently compute it?

What if we just sort full LMS substrings in alex order, and then label them? Namely, compute an array 𝑋X of length 𝑚m where 𝑃𝑋𝑖 ⪯𝑃𝑋𝑗∀𝑖 ≤𝑗PXi⪯PXj∀i≤j, and 𝑋𝑖Xi is an LMS position in 𝑇T for all 𝑖i. Consider the following procedure:

N = |T|

somehow compute X

R = [-1] * N
label = -1, last = -1

for i in X:
    if last == -1 or !equal(P[last], P[i])
        label += 1
    R[i] = label
    last = i

One concern is that assuming 𝑋X is given to us, is the labelling procedure efficient? What if the equal(A, B) function is implemented naively, i.e. in 𝑂(|𝐴| +|𝐵|)O(|A|+|B|) time? Since each full LMS substring contributes its length at most twice, and ∑|𝑃𝑙𝑖| =𝑂(𝑛)∑|Pli|=O(n), the total time taken is 𝑂(𝑛)O(n).

Alright, so we just need to sort full LMS substrings under alex now. It shouldn't be surprising that we'll lean on the machinery (L and S induce) we built for sorting suffixes previously. Further, we'll sort all LMS substrings, and then just extract the subsequence of full LMS substrings from this sorted order.

Let's state our goal more formally. We want to compute array 𝐶C of length 𝑛 +1n+1, which will contain every index in [0,𝑛][0,n] exactly once, and satisfy 𝑖 ≤𝑗 ⟹ 𝑇[𝐶𝑖,𝐸𝐶𝑖] ⪯𝑇[𝐶𝑗,𝐸𝐶𝑗]i≤j⟹T[Ci,ECi]⪯T[Cj,ECj]. A "partial suffix array" of sorts.

Now, consider the L-induce, which was previously used to sort L-type suffixes. Can we repurpose it to sort L-type LMS-substrings instead? When we previously discussed it, we seeded 𝐴A with 𝐺G, which contained the sorted order of all the LMS suffixes. Why? Because for every L-type suffix 𝑇[𝑖,𝑛]T[i,n], its final position in 𝐴A depended on the LMS suffix 𝑇[𝐸𝑖,𝑛]T[Ei,n] having been seeded correctly relative to the other LMS suffixes. In a certain sense, the position of 𝑇[𝐸𝑖,𝑛]T[Ei,n] (relative to other LMS suffixes) was storing all that the L-induce needed about its value when implicitly comparing 𝑇[𝑖,𝑛]T[i,n] against other suffixes.

But now that we're sorting 𝑇[𝑖,𝐸𝑖]T[i,Ei] instead of 𝑇[𝑖,𝑛]T[i,n], would it do to seed our array with 𝑇[𝐸𝑖,𝐸𝑖]T[Ei,Ei] instead?

The answer is yes, but we'll need to first prove some facts about LMS substrings.

Theorem 5.1

For any LMS-substring 𝑇[𝑖,𝐸𝑖]T[i,Ei] with 𝑖 ≠𝑛i≠n, its second-to-last character is strictly greater than the last.

This is just theorem 3.1 again, but it's quite fundamental to our arguments ahead, so I restate it.

Theorem 5.2

If position 𝑖i is L-type, then 𝑇[𝑖 +1,𝐸𝑖] ≺𝑇[𝑖,𝐸𝑖]T[i+1,Ei]≺T[i,Ei].

Proof

Since position 𝑖i is L-type, 𝑖 +1i+1 can either be L or LMS-type.

  • If 𝑖 +1i+1 is LMS type, then 𝑇𝑖 >𝑇𝑖+1 ⟹ 𝑇[𝑖 +1,𝐸𝑖] ≺𝑇[𝑖,𝐸𝑖]Ti>Ti+1⟹T[i+1,Ei]≺T[i,Ei]
  • Otherwise, 𝑇𝑖 ≥𝑇𝑖+1Ti≥Ti+1.
    • If 𝑇𝑖 >𝑇𝑖+1Ti>Ti+1, then 𝑇[𝑖 +1,𝐸𝑖] ≺𝑇[𝑖,𝐸𝑖]T[i+1,Ei]≺T[i,Ei] trivially.
    • Otherwise, we know that for the smallest 𝑥 ≥0x≥0 where 𝑇𝑖+𝑥 ≠𝑇𝑖+𝑥+1Ti+x≠Ti+x+1, we have 𝑇𝑖+𝑥 >𝑇𝑖+𝑥+1Ti+x>Ti+x+1 (definition of L-type suffixes). Since 𝑇𝐸𝑖−1 ≠𝑇𝐸𝑖TEi−1≠TEi, we must have 𝑖 +𝑥 +1 ≤𝐸𝑖i+x+1≤Ei, and the two strings differ before either ends.

Theorem 5.3

(Analogue of theorem 2.4) If 𝑇𝑖 =𝑇𝑗Ti=Tj, suffix 𝑖i is of L-type, and suffix 𝑗j is of S-type, then 𝑃𝑖 ≺𝑃𝑗Pi≺Pj.

Proof

Consider the proof of theorem 2.4. It applies to any strings which have prefixes of the form [>= 1 occurrences of b][1 occurrence of a]... and [>= 1 occurrences of b][1 occurrence of c]... respectively. We know that 𝑆𝑖Si and 𝑆𝑗Sj have this form, but do 𝑃𝑖Pi and 𝑃𝑗Pj do?

Since 𝑃𝑖Pi is a prefix of 𝑆𝑖Si, the only way it cannot be of this form is if it consists only of 𝑏b-s. But since 𝑃𝑖 =𝑇[𝑖,𝐸𝑖]Pi=T[i,Ei] contains both 𝑇𝐸𝑖−1TEi−1 and 𝑇𝐸𝑖TEi, and 𝑇𝐸𝑖−1 >𝑇𝐸𝑖TEi−1>TEi, it cannot possibly consist of only one character.

The same argument applies to 𝑃𝑗Pj.

Therefore, the two must have the same form and the proof of theorem 2.4 applies.

Consequently, 𝐶C can be divided into buckets just like 𝐴A. That is, it takes the following form:

  • First, we have L-type LMS-substrings that start with symbol 00.
  • Then, we have S-type LMS-substrings that start with symbol 00.
  • Then, L-type LMS-substrings that start with symbol 11.
  • Then, S-type LMS-substrings that start with symbol 11.
  • Then, L-type LMS-substrings that start with symbol 22.
  • Then, S-type LMS-substrings that start with symbol 22.
  • ...and so on

Now, let's try to adapt our old procedure 2 to produce 𝐶C:

Procedure 5 
C = [-1] * (n + 1)

put {T[i, i], i} for all LMS-type i into heap H, which uses the alex comparator

# just like our previous extend2 function, except here we insert T[j, E[j]] into the heap
def extend2(i):
    j = i - 1
    if (j >= 0) and (position j is L-type)
        place j in the first empty position of the bucket of T[j] in C
        put {T[j, E[j]], j} into H

while H is not empty:
    pop out {v, i}, the smallest element of H
    extend2(i)

The proof for procedure 5 correctly filling the L-regions of 𝐶C is quite similar to that for procedure 2 correctly producing 𝐴A.

First, notice that the deletion of any string from the heap can only result in the insertion of a strictly larger substring under alex (or no insertion at all):

  • If the string being deleted is 𝑇[𝑖,𝑖]T[i,i] with LMS 𝑖i, then by theorem 5.1, we have 𝑇[𝑖,𝑖] ≺𝑇[𝑖 −1,𝐸𝑖−1]T[i,i]≺T[i−1,Ei−1].
  • Otherwise, 𝑇[𝑖,𝐸𝑖]T[i,Ei] (𝑖i is L-type) being deleted results in the insertion of 𝑇[𝑖 −1,𝐸𝑖−1]T[i−1,Ei−1], then 𝑇[𝑖,𝐸𝑖] ≺𝑇[𝑖 −1,𝐸𝑖−1]T[i,Ei]≺T[i−1,Ei−1] (theorem 5.2).

Since we always erase the alex-smallest substring from the heap, the order in which we delete LMS substrings from the heap is alex-non-decreasing. Coverage (every L-type LMS substring is inserted into the heap at some point) is also guaranteed for the same reason as before.

Now, consider any two L-type LMS substrings 𝑇[𝑖,𝐸𝑖]T[i,Ei] and 𝑇[𝑗,𝐸𝑗]T[j,Ej]. We will show that their relative position in 𝐶C aligns with the result of their comparison under alex.

  • If 𝑇[𝑖,𝐸𝑖] =𝑇[𝑗,𝐸𝑗]T[i,Ei]=T[j,Ej], then their relative order doesn't matter.
  • Otherwise, if 𝑇𝑖 ≠𝑇𝑗Ti≠Tj, WLOG assume 𝑇𝑖 <𝑇𝑗Ti<Tj. Then we necessarily have 𝑇[𝑖,𝐸𝑖] ≺𝑇[𝑗,𝐸𝑗]T[i,Ei]≺T[j,Ej], and the two are placed in different buckets, with the former's bucket lying to the left of the latter's.
  • Otherwise, if 𝑇𝑖 =𝑇𝑗Ti=Tj, then 𝑇[𝑖,𝐸𝑖]T[i,Ei] and 𝑇[𝑗,𝐸𝑗]T[j,Ej] will be placed in the same bucket. Recall that for any character 𝑐c and strings 𝐴,𝐵A,B, we have 𝑐𝐴 ≺𝑐𝐵 ⟺ 𝐴 ≺𝐵cA≺cB⟺A≺B. Therefore, 𝑇[𝑖,𝐸𝑖] ≺𝑇[𝑗,𝐸𝑗] ⟺ 𝑇[𝑖 +1,𝐸𝑖] ≺𝑇[𝑗 +1,𝐸𝑗]T[i,Ei]≺T[j,Ej]⟺T[i+1,Ei]≺T[j+1,Ej]. Note that we cannot have 𝑇[𝑖 +1,𝐸𝑖] =𝑇[𝑗 +1,𝐸𝑗]T[i+1,Ei]=T[j+1,Ej] here. Consider the other two cases
    • If 𝑇[𝑖 +1,𝐸𝑖] ≺𝑇[𝑗 +1,𝐸𝑗]T[i+1,Ei]≺T[j+1,Ej], then the former is deleted before the latter from the heap, and 𝑇[𝑖,𝐸𝑖]T[i,Ei] is placed in their common bucket before 𝑇[𝑗,𝐸𝑗]T[j,Ej]. Since we also have 𝑇[𝑖 +1,𝐸𝑖] ≺𝑇[𝑗 +1,𝐸𝑗] ⟹ 𝑇[𝑖,𝐸𝑖] ≺𝑇[𝑗,𝐸𝑗]T[i+1,Ei]≺T[j+1,Ej]⟹T[i,Ei]≺T[j,Ej] here, their relative order in 𝐶C is valid.
    • If 𝑇[𝑗 +1,𝐸𝑗] ≺𝑇[𝑖 +1,𝐸𝑖]T[j+1,Ej]≺T[i+1,Ei], then the former is deleted before the latter from the heap, and 𝑇[𝑗,𝐸𝑗]T[j,Ej] is placed in their common bucket before 𝑇[𝑖,𝐸𝑖]T[i,Ei]. Since we also have 𝑇[𝑗 +1,𝐸𝑗] ≺𝑇[𝑖 +1,𝐸𝑖] ⟹ 𝑇[𝑗,𝐸𝑗] ≺𝑇[𝑖,𝐸𝑖]T[j+1,Ej]≺T[i+1,Ei]⟹T[j,Ej]≺T[i,Ei] here, their relative order in 𝐶C is valid.

This implies 𝑖 ≤𝑗 ⟹ 𝑇[𝐶𝑖,𝐸𝐶𝑖] ⪯𝑇[𝐶𝑗,𝐸𝐶𝑗]i≤j⟹T[Ci,ECi]⪯T[Cj,ECj] for the placed L-type LMS substrings 𝐶𝑖,𝐶𝑗Ci,Cj so far.

The observant reader will have noticed that our arguments have been almost identical to the initial use of L-induce. We shall continue in a similar vein. Consider this optimised version of procedure 5 (adapted from procedure 2.5):

Procedure 5.5 
C = [-1] * (n + 1)

put {T[i, i], i} for all LMS-type i into heap H

# once again, we don't place anything into the heap any more
def extend2(i):
    j = i - 1
    if (j >= 0) and (position j is L-type)
        place j in the first empty position of the bucket of T[j] in C

# we iterate over the first character of the suffix
for character c from 0 to n:

    # we first process the L-region of c
    let C[l, r] be the L-region for c
    for i from l to r:
        extend2(C[i])
  
    # we then process the LMS-types of c, naively
    while H is not empty and the smallest string in H begins with c:
        pop out {T[i, i], i}, the smallest element of H
        extend2(i)

Why is this correct? The proof is almost identical to that of procedure 2.5 - extend2(i) is called over the same sequence of 𝑖i. The only subtlety is that while the strings in 2.5 were suffixes and could therefore not be equal to each other, strings here can be equal. Fortunately, the order in which equal strings are processed doesn't matter at all (so it's technically not the exact same sequence of 𝑖i, you can swap indices which correspond to the same string). All of this should be fairly natural by now, so I'll leave the formal proof to the reader.

Now, recall that at this point in the old L-induce, we revealed the need for 𝐺G, as in procedure 2.5, we needed the heap to sort the LMS suffixes 𝑇[𝐸𝑖,𝑛]T[Ei,n] for us. But now? We're only using the heap to sort 𝑇[𝐸𝑖,𝐸𝑖]T[Ei,Ei]! There's no chicken-and-egg problem like before with 𝑇[𝐸𝑖,𝑛]T[Ei,n], because since these are just length-1 strings, we can easily sort them in 𝑂(𝑛)O(n) using counting-sort instead!

This allows us to easily optimise procedure 5.5 to the following 𝑂(𝑛)O(n) procedure (note that we don't explicitly sort 𝑇[𝐸𝑖,𝐸𝑖]T[Ei,Ei], instead we just place each LMS position at the tail of its respective bucket).

Procedure 6 
// Given n, T, and the bucket boundaries (see code in theorem 2.4)
int n;
vector<int> T, head, tail;

vector<int> C(n + 1, -1);

// Seeding - we put LMS positions at the tails of their S-buckets 
for(int i = 0; i <= n; i ++)
    if(is_LMS_type(i))
        C[--tail[T[i]]] = i;

auto extend2 = [&](int i) -> void
{
    int j = i - 1;
    if(j >= 0 and is_L_type(j))
    {
        C[head[T[j]]] = j;
        head[T[j]] ++;
    }
};

// induce L positions into C
auto l_induce = [&]() -> void
{
    for(int i = 0; i <= n; i ++)
        if(C[i] != -1)
            extend2(C[i]);
};
l_induce();

// clean up LMS types from C
for(int i = 0; i <= n; i ++)
    if(C[i] != -1 and is_LMS_type(C[i]))
        C[i] = -1;

The justification of its correctness is basically identical to that of procedure 3, and is left as an exercise to the reader.

Now that we have filled the L-regions of 𝐶C, we turn our attention back to the S-regions. A (perhaps) surprising fact - we don't need to change anything at all about procedure 4. Running the S-induce on 𝐶C now will correctly compute the S-regions!!

Once again, the proof is very similar to what we've done before (the changes relative to the previous S-induce are just that 𝑖i now represents 𝑃𝑖Pi instead of 𝑆𝑖Si and strings can therefore be equal), and is left as an exercise to the reader.

And... we end up with 𝐶C, correctly and efficiently computed.

6. Putting it all together

Let's finally assemble our algorithm from the pieces we've painstakingly built:

# T satisfies conditions from section 1
SA(T):
    N = |T|
    n = N - 1

    if N == 1:
        return [0]

    classify L, S, LMS types in O(n)

#PHASE 1: sort LMS substrings under alex
    C = [-1] * (n + 1)
    seed C with T[i, i] for all LMS positions i, in O(n)
    run L induce on C   # we compute fresh bucket boundaries before every L and S induce
    run S induce on C

#PHASE 2: construct T2 and sort its suffixes to get G
    #label full LMS substrings
    R = [-1] * (n + 1)
    label = -1, last = -1
    for i from 0 to n:
        if C[i] is LMS type:
            j = C[i]
            if last == -1 or !equal(last, j):     #equal(i, j) compares P[i] and P[j]
                label += 1
            R[j] = label
            last = j
    #construct T2 and sort its suffixes
    T2 = []
    for i from 0 to n:
        if i is LMS type:
            T2.append(R[i])
    A2 = SA(T2)
    #construct G from A2
    G = A2
    for i from 0 to |G| - 1:
        G[i] = l[G[i]]  #l[i] is i-th LMS position in T

#PHASE 3: seed A with G and run the final L and S induce 
    A = [-1] * (n + 1)
    seed A with G
    run L induce on A
    run S induce on A

    return A

My own implementation of SAIS was unfortunately created before I wrote this blog, and doesn't really follow the exposition, but here's a highly readable one by my friend Opus 5.5 that does:

Code 
#include <bits/stdc++.h>
using namespace std;

// Types of positions (section 2, 3). An LMS position is also S-type.
enum Type : uint8_t { L_TYPE, S_TYPE, LMS_TYPE };

// Computes the suffix array of T.
// T must satisfy the conditions from section 1: with n = |T| - 1,
//   - T[n] == 0 is the sentinel (the unique minimum), and
//   - T[i] lies in [1, n] for all i < n.
vector<int> SA(const vector<int> &T)
{
    const int N = (int)T.size(), n = N - 1;

    // base case
    if(N == 1)
        return {0};

    // ---------------------------------------------------------------
    // Classify positions as L / S / LMS (theorem 2.3, section 3)
    // ---------------------------------------------------------------
    vector<Type> Q(N);
    Q[n] = S_TYPE;
    for(int i = n - 1; i >= 0; i --)
    {
        if(T[i] < T[i + 1])
            Q[i] = S_TYPE;
        else if(T[i] > T[i + 1])
            Q[i] = L_TYPE;
        else
            Q[i] = Q[i + 1];
    }

    vector<int> l;      // l[k] = k-th LMS position, so l = {l_0 < l_1 < ... < l_{m - 1}}
    for(int i = 1; i <= n; i ++)
        if(Q[i] == S_TYPE and Q[i - 1] == L_TYPE)
        {
            Q[i] = LMS_TYPE;
            l.push_back(i);
        }
    const int m = (int)l.size();

    auto is_L_type = [&](int i) { return Q[i] == L_TYPE; };
    auto is_S_type = [&](int i) { return Q[i] != L_TYPE; };
    auto is_LMS_type = [&](int i) { return Q[i] == LMS_TYPE; };

    // ---------------------------------------------------------------
    // Bucket boundaries (section 2): the bucket for symbol c is [head[c], tail[c])
    // ---------------------------------------------------------------
    vector<int> cnt(N, 0);      // symbols lie in [0, n]
    for(int x : T)
        cnt[x] ++;

    // induce L/S both modify the boundaries, so we hand out fresh copies every time
    auto get_buckets = [&](vector<int> &head, vector<int> &tail) -> void
    {
        head.assign(N, 0);
        tail.assign(N, 0);
        for(int c = 0, sum = 0; c < N; c ++)
        {
            head[c] = sum;
            sum += cnt[c];
            tail[c] = sum;
        }
    };

    // ---------------------------------------------------------------
    // Induced sorting (section 4)
    //
    // `seeds` contains the LMS positions, in sorted order. Returns the array
    // obtained by seeding them at the tails of their S-buckets, then running
    // L-induce (procedure 3) followed by S-induce (procedure 4).
    //
    // Phase 1 and phase 3 differ *only* in the seeds they pass here.
    // ---------------------------------------------------------------
    auto induced_sort = [&](const vector<int> &seeds) -> vector<int>
    {
        vector<int> A(N, -1);
        vector<int> head, tail;

        // seeding: walk the seeds from largest to smallest, filling each S-bucket from its tail
        get_buckets(head, tail);
        for(int k = (int)seeds.size() - 1; k >= 0; k --)
        {
            int i = seeds[k];
            A[-- tail[T[i]]] = i;
        }

        // L-induce: walk left to right; if A[i] - 1 is L-type, append it to the
        // first free slot of its L-bucket (this is extend2)
        for(int i = 0; i < N; i ++)
        {
            if(A[i] == -1)
                continue;
            int j = A[i] - 1;
            if(j >= 0 and is_L_type(j))
                A[head[T[j]] ++] = j;
        }

        // clean up: remove the seeded LMS positions, the S-induce places them again
        for(int i = 0; i < N; i ++)
            if(A[i] != -1 and is_LMS_type(A[i]))
                A[i] = -1;

        // S-induce: walk right to left; if A[i] - 1 is S-type, prepend it to the
        // last free slot of its S-bucket (this is extend3)
        get_buckets(head, tail);
        A[0] = n;               // the sentinel is the smallest suffix, place it manually
        for(int i = n; i >= 0; i --)
        {
            if(A[i] == -1)
                continue;
            int j = A[i] - 1;
            if(j >= 0 and is_S_type(j))
                A[-- tail[T[j]]] = j;
        }

        return A;
    };

    // ---------------------------------------------------------------
    // PHASE 1: sort all LMS substrings under alex (section 5.2)
    //
    // Seeding with T[i, i] for each LMS position i: these are single
    // characters, so any order works, as long as each one lands in its own
    // bucket (procedure 6).
    // ---------------------------------------------------------------
    vector<int> C = induced_sort(l);

    // ---------------------------------------------------------------
    // PHASE 2: label full LMS substrings, build T2, recurse (sections 5.1, 6)
    // ---------------------------------------------------------------

    // equal(i, j) checks whether P_i == P_j for LMS positions i != j.
    // P_i = T[i, E_i] ends at the next LMS position, so we walk both substrings
    // together until one of them ends. They are equal iff both end at the same
    // offset with all characters equal along the way.
    // (If one of them is the sentinel n, the very first characters differ, so
    // we never read past the end of T.)
    auto equal = [&](int i, int j) -> bool
    {
        for(int k = 0; ; k ++)
        {
            if(T[i + k] != T[j + k])
                return false;
            bool end_i = (k > 0 and is_LMS_type(i + k));
            bool end_j = (k > 0 and is_LMS_type(j + k));
            if(end_i or end_j)
                return end_i and end_j;
        }
    };

    // walk C (which is alex-sorted) and give equal full LMS substrings equal labels
    // R[i] = label of P_i, for LMS positions i
    vector<int> R(N, -1);
    int label = -1, last = -1;
    for(int k = 0; k < N; k ++)
    {
        int j = C[k];
        if(!is_LMS_type(j))
            continue;
        if(last == -1 or !equal(last, j))
            label ++;
        R[j] = label;
        last = j;
    }
    // C[0] = n is the first LMS position seen, so the sentinel gets label 0,
    // and every other label lies in [1, m - 1]: T2 satisfies section 1

    // T2[k] = label of the k-th full LMS substring
    vector<int> T2(m);
    for(int k = 0; k < m; k ++)
        T2[k] = R[l[k]];

    // G = LMS positions in sorted order of their suffixes
    vector<int> G = SA(T2);
    for(int k = 0; k < m; k ++)
        G[k] = l[G[k]];

    // ---------------------------------------------------------------
    // PHASE 3: seed with G and induce the actual suffix array (section 4)
    // ---------------------------------------------------------------
    return induced_sort(G);
}

// Convenience wrapper for arbitrary non-negative input: s[i] in [0, K).
// Remaps s to satisfy section 1 in O(n + K), and drops the sentinel from the result.
vector<int> suffix_array(const vector<int> &s, int K)
{
    const int n = (int)s.size();

    // rank[x] = 1 + number of distinct symbols in s smaller than x
    vector<int> rank(K, 0);
    for(int x : s)
        rank[x] = 1;
    for(int x = 0, r = 0; x < K; x ++)
        if(rank[x])
            rank[x] = ++ r;

    vector<int> T(n + 1);
    for(int i = 0; i < n; i ++)
        T[i] = rank[s[i]];
    T[n] = 0;

    vector<int> A = SA(T);
    return vector<int>(A.begin() + 1, A.end());     // A[0] is always the sentinel
}
